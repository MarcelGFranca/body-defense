## Context

The repository has no Godot project yet. The game is a portrait Android tower defense with a pixelated 16-bit look and "a little 3D". See `proposal.md` for the motivation, `specs/enemy-roster/spec.md` and `specs/economy/spec.md` for the requirements. This change defines enemy data and the economy; behavior such as movement, waves and trait logic comes later.

## Goals / Non-Goals

**Goals:**
- One data file per enemy, editable without touching code.
- A simple validation that guarantees the full roster and the mandatory attributes.
- One place that owns the amino acid balance, so spending, earning and refunds all go through the same checks.
- Drops that feel good on mobile: automatic collection with a short fly-to-counter animation.
- A structure that lets ATP be added later without changing how amino acids work.

**Non-Goals:**
- Implementing trait behavior (splitting, spores, sabotage and so on). Here they are only described in data.
- Implementing ATP, its abilities or its UI. It is only reserved in the spec.
- Final balance values, tower prices and reward amounts: all numbers are provisional.
- Final art, and tap-to-collect drops (can be tested later if auto-collect feels too passive).

## Decisions

- **One Godot `Resource` (`.tres`) per enemy, with an `EnemyData` script.** Alternative: a single JSON file. A `Resource` shows up in the editor, is type-checked and can reference textures and scenes later. JSON would be easier to generate in bulk, but loses visual editing.
- **Folder `data/enemies/<id>.tres`, with the identifier equal to the one in the spec.** Makes the roster easy to find and validate by file name.
- **Trait as a text identifier (`trait_id`) plus a description, with no logic.** Logic will be wired by `trait_id` in a later change, without touching the data files.
- **Validation as a command-line script (`godot --headless --script`).** Runs without opening the editor, checks the 13 files, and can go into CI later.
- **Files generated by a batch script from a single table, then maintained by hand.** Avoids typos across 13 files.
- **Portrait Godot project (720×1280) with Nearest texture filtering.** Base configuration only; the low-resolution `SubViewport` belongs to the game scene change.
- **A single `Economy` node (autoload) holding the balance.** Alternative: store the balance inside each level scene. An autoload is simpler to reach from enemies, towers and the HUD, and can be reset at level start.
- **Spending goes through `try_spend(amount)`, which returns whether it worked.** Alternative: let callers subtract directly. The single entry point enforces "never negative" in one place.
- **Drops are visual only; the balance changes at the moment of death.** The orbs fly to the counter for feedback, but the amino acids are already added. This avoids losing money if the level ends while orbs are still flying.
- **Currencies are keyed by id in a dictionary (`amino_acids`, later `atp`).** Alternative: one variable per currency. A dictionary lets ATP be added without new plumbing, while the spec keeps ATP hidden until enabled.
- **Refund fraction and starting amount live in data resources,** in line with the rule that balance values are editable without touching code.

## Risks / Trade-offs

- [Unbalanced starting numbers] → Marked as provisional and isolated in data files, easy to tweak.
- [A trait is hard to implement later] → Each has a clear role in the table; costly ones can be simplified without changing the roster.
- [Technical names are not very recognizable to players] → The display name is separate from the identifier, so popular names (for example "Flu") can be used without breaking anything.
- [Auto-collect makes drops feel less rewarding] → Keep the orb animation and a small sound; revisit tap-to-collect after playtesting.
- [Early economy is too generous or too tight] → All numbers are provisional data, tuned during prototype playtests.
- [A deferred spec section can be forgotten] → The spec scenarios define exactly what "not enabled" means, so a future change can turn it on deliberately.
